# SDG-RE 需求规格 · feature-007 数据治理（消息流瘦身与业务事实源分离）

> 版本：v1.0（2026-10-04 起草）
> 关联：feature-006-通用产物查看（定稿回退能力是本次分离的前置）、feature-001~005（各产物生产与变更传播）
> 触发：用户连续两次质疑——「立项信息都存到 chat.messages.json，以后清空对话记录，立项信息不都没有了」「为什么 chat.messages.json 要设计成业务数据源，它应该只是对话的数据源吗」。

## 1. 背景与问题

### 1.1 历史成因：一次未经论证的合并

[短剧Agent平台设计.md](../../../短剧Agent平台设计.md) 的原始架构中，可重放的流程事件流载体是独立的 `events.log`（事件 `{时间, agent, 类型, 载荷, 关联节点}`），与 Agent 对话分离。

落地 feature-002 时，对话与流程事件被合并写入同一个 `chat.messages.json`；feature-004 后才在设计文档 §7.1 以「实现真相」追认该文件为「唯一事实源」。**全量核查 feature-001~006 变更记录，没有任何一条决策记录论证过这次合并**——它是落地简化的既成事实，而非原始契约。

### 1.2 消息流当前混装三类数据

| 类别 | 内容 | 是否越界 |
| :-- | :-- | :-- |
| ① 纯对话 | `kind: text`（用户气泡 / Agent 文本） | 合理，本就属于对话 |
| ② 业务产物 | diagnosis / visual-style / story-outline / character-profiles / scenes / dialogue / storyboard（**完整产物放消息 data**） | **真正越界**：这是业务数据，不是对话 |
| ③ 流程控制事件 | gate / gate-action / stage / archive / unlock / revision | 合理的事件日志内核 |

### 1.3 由此产生三个问题

1. **清空对话会摧毁业务**：未来若提供「清空对话」，② 业务产物随之消失，立项/故事/剧本成果全部丢失；
2. **双源、双份数据**：feature-006 后定稿产物同时存在于消息流与独立定稿文件，两处各一份，存在不一致与歧义风险（feature-006 用「消息流优先、定稿兜底」临时缓解，未根治）；
3. **职责边界不清**：一个名为「对话消息」的文件实际承担业务事实源职责，恢复逻辑（`replayMessages`）必须深度依赖消息里的完整产物，无法独立看待。

## 2. 目标

1. **独立定稿文件成为业务产物的唯一事实源**：业务数据以会话目录下的 JSON 文件为准，下游 Agent、查看器、画布都从文件取数；
2. **`chat.messages.json` 回归对话本体**：只承担「对话展示」，产物卡片仍可上屏但不再是事实源，清空/丢失消息流不损伤任何业务；
3. **工作流运行态可恢复**：节点 done/active/invalidated、phase、活动变更链、待处理门等从持久化状态恢复，不再靠消息流折叠；
4. **补齐 idea / diagnosis 的独立持久化**：消除 feature-006 US-8 的两条「不可回退硬边界」；
5. **存量会话平滑迁移**：旧项目在首次打开时一次性迁移，已有成果不丢失。

## 3. 用户故事与场景

| # | 角色 | 场景 | 期望 |
| :- | :-- | :-- | :-- |
| US-1 | 导演 | 清空了全部对话记录后重新打开项目 | 业务产物（创意/诊断/立项单/大纲/小传/分场/台词/分镜）全部仍在，节点为定稿态，可查看、可继续生产 |
| US-2 | 导演 | 正常关闭后重开项目 | 不依赖消息流折叠，直接从定稿文件 + 持久化工作流状态恢复全部画面，结果与旧 replay 一致 |
| US-3 | 导演 | 想清空冗长对话，让界面干净 | 提供「清空对话」入口；清空只移除对话气泡，业务成果与已提交的变更链保留 |
| US-4 | 导演 | 任意时点点开产物查看（与对话是否清空无关） | 内容统一来自独立定稿文件，标题「来源」始终显示对应文件，而非 chat.messages.json |
| US-5 | 导演 | 打开一个旧项目（feature-007 之前创建） | 首次打开自动一次性迁移：补建 idea/diagnosis 文件与工作流状态，此后与新项目行为一致 |
| US-6 | 导演 | 在有未确认门/生成中/修改会话进行时点「清空对话」 | 操作被阻止并提示先处理进行中的事项，避免丢失未落定的交互 |

### US-1 / US-3：清空对话的精确语义

「清空对话」让工作流落在**最近一个已确认检查点**，可完全由「定稿文件 + 持久化工作流状态」恢复：

1. 删除 `chat.messages.json` 全部消息（文件重置为空数组）；
2. **保留**：全部独立定稿产物（idea.json / diagnosis.json / brief.json / 背景档案 / 剧本/* / 分镜/shotlist）与 manifest 工作流状态；
3. **重置为未进行**：待处理门（pendingGate）、进行中的修改会话（activeDraft）等一切「未落定的交互态」——这些本来就只存在于对话进行中，清空即放弃；
4. **保留变更链语义**：已提交 unlock 的 activeUnlock 与 invalidated 节点状态保留（旧版本文件在即可查看，invalidated 是真实状态而非临时态）。

**允许清空的前置条件（任一不满足则阻止并提示）**：

- 无正在进行的生成（`loading = false`）；
- 无待处理确认门（`gate = null`，含 pendingGate）；
- 无进行中的修改会话（`activeDraft = null`）；
- 无等待重做的门（redoGate / storyRedo / scriptRedo 均为 null）。

> 前置条件是 L2 设计决策（有多个可选语义），已在契约 §7 固化为此方案，卡口签字即确认。

### US-5：存量会话一次性迁移

对没有 manifest 工作流状态（`workflowVersion` 缺失）的旧会话，首次 hydrate 时：

1. 复用现有 `replayMessages` 从消息流折叠出全部状态（作为唯一一次的迁移函数）；
2. 据折叠结果补建 `idea.json`、`diagnosis.json`（此前无独立文件）；
3. 写入 manifest 工作流状态（`workflowVersion: 1`）；
4. 迁移幂等：重复打开不再重复迁移。

## 4. 功能范围

### 4.1 业务产物的持久化归属（唯一事实源）

| 数据 | 唯一事实源文件 | 写入时机 |
| :-- | :-- | :-- |
| 创意原文 ideaText | `idea.json`（新增） | 创意提交时（会话建立后立即写）；idea unlock 通过时覆盖 |
| 完整选题诊断 TopicDiagnosis | `diagnosis.json`（新增） | 诊断生成并在 0-a 门通过时写；idea unlock 后随重诊更新 |
| 立项六要素 + 视觉风格 + 结论 | `brief.json`（既有） | 0-c 门通过时（沿用现状） |
| 故事背景档案 | `故事背景档案.md`（既有） | 档案锁定时（沿用现状） |
| 大纲 / 小传 | `剧本/故事大纲.json`、`剧本/人物小传.json`（既有） | 1-a / 1-b 通过时（沿用现状） |
| 分场 / 台词 | `剧本/分场.json`、`剧本/台词.json`（既有） | 2-a / 2-b 通过时（沿用现状） |
| 分镜表 | `分镜/shotlist.json`（既有） | 2-c 通过时（沿用现状） |

> 未过门的 AI 候选产物（candidate）与门内待确认产物**不落**独立文件——它们属于「未落定交互」，随清空放弃，符合「只有定稿才是业务事实」。

### 4.2 工作流运行态持久化

扩展 `manifest.json`（既有文件，读-改-写保留既有字段）承载工作流快照，字段契约见 SDG-RE-契约 §3：

- `workflowVersion`、`phase`、`nodes`（10 节点状态）、`pendingGate`、`redoGate`、`storyRedo`、`scriptRedo`、`activeUnlock`、`activeDraft`、`feOverride`、`saved`；
- 每次发生门动作 / unlock / revision / 阶段进入等变化时，经现有单写队列写回；
- 正常 hydrate 直接读 manifest 工作流状态，不再折叠消息流。

### 4.3 消息流瘦身后的定位

1. `chat.messages.json` 为**纯展示/对话层**：对话气泡、进度、产物卡片仍照常 push 上屏与落盘，保证会话内可读性；
2. 消息流中的 ② 完整产物不再作为任何恢复/取数的事实源；
3. `replayMessages` 保留，但**仅服务存量迁移**（US-5），正常路径不再调用。

### 4.4 新增 IPC（均属 K8，见契约）

| IPC 通道 | 职责 |
| :-- | :-- |
| `workflow:save` | 原子写回 manifest 工作流快照 |
| `idea:save` | 写 idea.json（写前归档到 版本/） |
| `diagnosis:save` | 写 diagnosis.json（写前归档到 版本/） |
| `chat:clear` | 清空对话 + 重置未落定交互态（语义见 US-1） |

`session:read-finalized`（feature-006）扩展返回 `idea` / `diagnosis` 两字段，成为 hydrate 的统一业务取数入口。

## 5. 非目标（一期不做）

- **不拆分独立 events.log**：流程事件保留在消息流中即可满足目标，不为「形式对齐原设计」而新增文件与双写成本；
- 不做产物版本历史列表 UI（沿用 feature-005/006 现状）；
- 不改变各 Agent 提示词、产物生产逻辑与门控判定规则；
- 不引入数据库，维持纯 JSON 文件持久化；
- 不做「清空对话」的撤销/回收站（清空前置条件已保证不丢业务，对话气泡清空即终态）。

## 6. 验收标准（摘要，详见任务清单 AC）

1. 新项目正常 hydrate 不调用消息流折叠，业务产物全部来自定稿文件，画面与旧 replay 结果一致；
2. idea.json / diagnosis.json 在对应时机写入，字段与消息流原产物一致；
3. 执行「清空对话」后：消息为空，全部业务产物仍在、可查看、可继续生产；
4. 查看器任意时点（与对话是否清空无关）均以独立定稿文件取数，「来源」始终显示独立定稿文件名；
5. 清空在有未确认门/生成中/修改会话/重做等待时被阻止并提示；
6. 旧会话首次打开自动迁移且幂等，迁移后 idea/diagnosis/工作流状态齐备；
7. unlock 变更链与 invalidated 节点在清空后语义保留；
8. 全量单元测试 + 双端 tsc + build 通过，无回归；
9. 卡口 K3/K6/K8 经用户签字，决策记录落账。
